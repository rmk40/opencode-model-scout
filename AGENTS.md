# Agent Instructions

OpenCode 2 plugin: discovers the models served by OpenAI-compatible providers, enriches them with limits, capabilities, input modalities, effort variants, and prices, and adds them to the model catalog through a model transform. A TUI half adds the `/modelscout` browser and the Actualyze-branded `/actualyze` dialog.

## Architecture

```
src/server.ts           → Server entry ({ id, setup }): loads stored bindings, registers transforms and RPC, starts the refresher
src/refresher.ts        → Per-instance driver: targets, triggers, periodic refresh, reloads, RPC catalog payload, plugin options
src/store.ts            → Process-wide discovery store on globalThis: bindings, jobs, generations, refresh throttle
src/actualyze.ts        → Built-in Actualyze provider record and its `actualyze` integration (key + ACTUALYZE_API_KEY)
src/transform.ts        → Provider transform (recorder + Actualyze provider), eligibility rule, two-pass model transform, Model.Info patching
src/discover.ts         → discoverProvider (network I/O for one target) and toModelInfo (pure mapping to patches + evidence)
src/models-dev-index.ts → models.dev matcher built from the host's provider source records
src/catalog-evidence.ts → Evidence schema (version 5) and strict validator shared by server and TUI
src/rpc.ts              → Plugin RPC contract: catalog, refresh, `updated` and `status` events
src/tui.ts              → TUI entry ({ id, setup }): registers /modelscout and /actualyze in a global keymap layer; cleanup closes both dialogs
src/tui-session.ts      → Browser dialog session: show/set, host and RPC reads, update feed, coalesced reloads, nav memory, refresh, copy, model picker handoff with a pre-filled search, notices, untracked render, theme effect, fallback view
src/tui-browser.ts      → Browser view: filters, search, sort, row projection, layout, screens, footer, key handling, frame hooks for /actualyze
src/tui-keys.ts         → Pure key router: screen + focus + KeyEvent fields → browser action
src/tui-detail.ts       → Model and provider details, Evidence, provider status and failure copy, key list lines
src/tui-list.ts         → Recycled row list (one StyledText node per row), column-aware text cells, selection and scroll
src/tui-theme.ts        → Color roles mapped to dialog-surface tokens; Actualyze brand color by theme mode
src/tui-actualyze.ts    → Pure /actualyze logic: endpoint origin and custom flag, app links, connection facts, pending-key reducer, state table, session tracker
src/tui-actualyze-view.ts → /actualyze sessions, header, status line, cards, links screen, key flow (a frame around the browser)
src/tui-models.ts       → Reconciles host model/provider rows with RPC evidence; certainty, price tiers, host temperature
src/tui-renderer.ts     → Typed imperative adapter over the host's @opentui/solid reconciler, plus setStyledText
src/format.ts           → Pure formatters (model names, compact counts, list and detail prices, bytes)
src/constants.ts        → Plugin ID, command names, Actualyze provider constants and app link paths, probe ID aliases, never-probed provider IDs, openai-compatible packages
src/probes/             → Probe implementations, registry, fingerprinting, shared HTTP helpers (see src/probes/AGENTS.md)
scripts/check-dist.mjs  → Fails when dist/*.js imports @opencode/* or effect at runtime
scripts/live-harness.mjs, scripts/live-check.mjs → Live checks against the installed opencode, with mock-compat and a key-selected Actualyze mock (not shipped, not in CI)
scripts/live-tui.mjs    → TUI scenarios through tuistory at 120x36 and 80x24, dark and light, with key-leak checks (not shipped, not in CI)
test/                   → Unit tests (vitest, global fetch mocked by test/setup.ts)
test/e2e/               → Embedded-host tests through @opencode/sdk (separate vitest config, real fetch)
```

The package exports `.` and `./server` → `dist/server.js`, `./tui` → `dist/tui.js`, and `./rpc` → `dist/rpc.js`. The host resolves `<package>/server` before `<package>` and loads `<package>/tui` automatically alongside the server half; there is no separate TUI config entry. `./rpc` exports the RPC contract for other clients. Both halves and the RPC contract share the ID `opencode-model-scout` (`PLUGIN_ID`); the host dedupes a package listed in both `opencode.json` and `cli.json` by that ID.

`@opentui/core` and `@opentui/solid` are optional peers and dev dependencies pinned to the version the host injects (0.5.17 for OpenCode 2.0.32); the TUI also imports `solid-js` from the host at runtime for `untrack` and `createEffect`. `@opencode/plugin` and `@opencode/sdk` are exact-pinned dev dependencies used for types and the E2E lane.

## Non-obvious Constraints

- **`@opencode/*` imports are type-only.** The host serves `@opencode/plugin` and `effect` to plugins and throws if a plugin loads either from its own `node_modules`. Never import a runtime value from `@opencode/*` (for example `Rpc.define`); `src/rpc.ts` is a plain object that `satisfies Rpc.PortableDefinition`. tsup keeps `@opencode/*`, `effect`, `@opentui/*`, and `solid-js` external, and `npm run check:dist` fails on any runtime import of the first two.
- **No network I/O in `setup`.** Plugins activate one at a time, so an awaited fetch in `setup` delays every later plugin, including the config provider plugin. `setup` reads storage, registers transforms and RPC, starts the refresher without awaiting it, and returns its cleanup.
- **Transforms are synchronous, pure, and must not throw.** A throwing transform disables every registration of the plugin. The model transform computes every patch inside `try`/`catch` first and only then calls `editor.update`, because editor updates mutate the candidate immediately and a failure halfway through would leave partial edits. `applyPatch` assigns every field scout controls, starting from a fresh default, so a replay on a fresh candidate yields the same model. Both callbacks replace what they record on each run, never accumulate, because the host can abandon a candidate and restart the fold.
- **Built-in Actualyze provider.** Every instance registers the integration `actualyze` (name "Actualyze", key method plus env `ACTUALYZE_API_KEY`) and adds an `actualyze` provider: `activation: "auto"`, `integrationID: "actualyze"`, package `@opencode/ai/providers/openai-compatible`, `settings.baseURL` `https://app.actualyze.ai/openai/v1`, `settings.probe` `actualyze`, no models. The host hides it until the integration has a connection, and the refresher only sees available providers, so nothing is probed without a key. The integration ID must equal the provider ID: the host's config provider plugin registers an integration under the provider ID for every `providers.<id>` entry unless one exists, and `opencode auth login actualyze` resolves by exact ID before name, so any other ID would give a configured `actualyze` provider a second integration that receives the key while the provider reads none. Accepted edge case: an `actualyze` provider that an earlier plugin defined with `activation: "auto"` and no `integrationID` is gated by the `actualyze` integration (the host hides such a provider while an integration with its ID exists and has no connection), so it stays hidden until a key is connected. Integrations and providers are folded separately, so the two guards are independent: the provider is skipped when an `actualyze` provider already exists (a models.dev catalog from `OPENCODE_MODELS_PATH`, or an earlier plugin), and the integration is skipped when an `actualyze` integration exists (a catalog registers one with its provider when it lists env vars), so `/connect` never shows two Actualyze entries. A pre-existing provider is in the recorded set and has no `settings.probe`, so it is not discovered unless config adds one. The config provider plugin runs after external plugins and merges settings key-wise over this record, so a configured `settings.baseURL` wins; any config entry also sets `activation: "enabled"`, which lists the provider without a key. The provider transform records the provider set before adding Actualyze, so the added provider never counts as pre-existing.
- **The provider recorder is per instance.** It records the provider IDs present before config providers load (models.dev templates, built-ins, earlier plugins). That set drives auto-eligibility. It lives in each instance's `TransformState`, never at module level, because provider state is per location. On a fresh process the first fold runs before config-only providers exist; a missing provider is normal and gets no patches.
- **The discovery store lives on `globalThis`.** The host evaluates the plugin module once per location in the same process, so module-level state is not shared. `sharedStore()` uses a versioned `Symbol.for` key. Jobs belong to the store, are keyed by the full target fingerprint (provider ID, normalized base URL, probe, API key hash, headers hash) plus, unless the target resolved to its `settings.apiKey`, the resolved credential fingerprint (`credentialKeys`: an integration connection hash, or `none`, hashed with the sync key into a separate key), and are aborted when their last subscriber leaves. (`invalidate` and the credential-mismatch branch of `start` also abort, but are defensive paths: a store key maps to one credential fingerprint.) Locations with different integration credentials therefore never share a job or a binding. Starts are throttled to one per minute per key, and none starts before the entry's `retryAt`, which a failed model list sets from `Retry-After` (429 or 503) or `X-RateLimit-Reset` (429), clamped to one hour, and a success clears; both are per key, so a 429 on one credential never delays another. An abort because the last subscriber left resets the one-minute throttle but keeps `retryAt`. A job result is accepted only while its generation is current.
- **Credential precedence matches inference.** The host's model resolver prefers the integration's active connection over `settings.apiKey`, so the refresher resolves each target in that order: the connection of `integrationID ?? providerID`, then `settings.apiKey`, then no key. A failed lookup keeps the previous integration or keyless resolution for that target, else falls back to `settings.apiKey`, else leaves the target unresolved for that sync (no discovery, catalog record `credentialSource: "unresolved"`); it never falls back to `none`. A `credential.switched` event revokes every resolution of the affected integration, including `settings.apiKey` ones, so a newly connected key takes over.
- **Serving goes only through the active binding.** The model transform cannot look up connections, so every target, with or without `settings.apiKey`, is served only through the instance's active binding (`TransformState.active`), which the refresher sets after resolving this instance's credential. At startup the first sync finds a persisted binding for the resolved key and activates it without discovery.
- **`ctx.storage` is global per plugin ID, not per location.** Persisted bindings are keyed by the same store key and hold hashes and inventories only, never keys or headers. `loadPersisted` keeps the newest 128 and removes malformed entries. Bindings from an integration credential stay unverified until the refresher confirms the same credential.
- **Eligibility.** A target needs `settings.baseURL` plus either `settings.probe`, or the auto rule: absent from the recorded set, no `canonical`, and an openai-compatible package (`OPENAI_COMPATIBLE_PACKAGES`). `ollama`, `lmstudio`, `vllm`, and `opencode` are never targets (`NEVER_PROBED_PROVIDER_IDS`). The absence check is a heuristic: a provider plugin listed after scout also looks absent.
- **Declared models are never patched.** Any model ID already in the provider's source record (config or models.dev) is reported as `pre-existing` evidence and left untouched.
- **Credential changes rekey.** OpenCode does not publish `provider.updated` when an account switch leaves provider availability unchanged, so `credential.switched` and `credential.updated` are triggers. `credential.switched` is published without a location; the event filter passes unlocated events. A switch revokes this instance's credential resolution for each affected target at once: it drops the active binding, unsubscribes from the old store key, and marks the target's record `unresolved` with a new epoch, so the target serves nothing until a sync resolves the new credential, and a failed lookup after a switch leaves the target unresolved instead of reusing the old account. It never invalidates store entries: each is keyed by its credential and other locations may still use it; an old-credential job is aborted only if this instance was its last subscriber. Notifications for a key the instance no longer resolves to are ignored, and a sync drops any integration resolution that a switch arriving during its lookup may have superseded. The next sync resolves the new credential, which selects a different store key. A reload publishes only `model.updated`, which is not a trigger, so reloads cannot loop.
- **Catalog records outlive credential resolution.** The refresher keeps record state per provider ID in a map that outlives each sync's `targets`, so every eligible provider keeps its catalog record through a credential switch and a failed lookup. A record with nothing resolved is `unresolved`; it, and a record whose credential changed and whose new store key has no result yet, carry status fields only (no models, `lastGoodAt` and `failure` null), so the previous credential's inventory never appears under the new one. `credentialEpoch` increments per provider ID whenever the resolved credential identity (endpoint key plus credential fingerprint, so `settings.apiKey` and header edits count, probe-only edits do not) changes, including to `unresolved`; `resultEpoch` becomes `credentialEpoch` whenever the current store key has no running job and holds a binding or a failure, whichever location or stored binding produced it. Records are status only: serving still goes only through the active binding.
- **Catalog v5 and the `status` event.** The payload carries a random `instanceID` per refresher, `generatedAt`, and `builtIn.actualyze` (`foreign` only when an `actualyze` provider existed before scout's provider transform and is not a discovery target; the provider transform records whether it added the provider on every fold). Records carry `discovering`, `lastAttemptAt`, `nextRefreshAt` (the later of the last start plus one minute and `retryAt`, or null once past), `credentialSource` (`headers` when provider headers replace the key: `authorization` or `x-actualyze-api-key` for the Actualyze probe, `authorization` or `x-api-key` otherwise), and the epochs. Failures are `{ kind, at, httpStatus?, retryAt? }`; HTTP kinds (`unauthorized`, `forbidden`, `payment-required`, `rate-limited`, `not-found`, `server-error`, `http-error`) carry exactly their status, and `timeout` covers the job budget and the list request's header and body timers. The list fetch uses the typed `fetchOutcome`/`readJsonOutcome` helpers; probes keep `probeFetch`/`readJson`. The `status` event (`{ at }`, one per turn) fires when this instance starts or joins a job, when any location starts a job on a store key this instance subscribes to (the store's `started` update reaches every subscriber), when credential resolution changes an epoch, and when a job settles (after the reload for a binding); `updated` keeps its meaning.
- **`limit.output: 0` means unknown.** `Model.Info` requires both limits. Scout emits the probe's output limit (capped at context) or `0`, which the host treats as "fit to the remaining context". Unknown context uses the host default of 200 000 and is labeled `host default` in evidence.
- **Effort variants.** Reasoning models on an openai-compatible package get `low`/`medium`/`high` with `settings.reasoningEffort`. Actualyze models get none: its chat endpoint does not forward `reasoning_effort`.
- **Never dump `model.list` or `provider.list` responses.** Both include provider settings with the plaintext `apiKey`. Scripts and tests print only the fields they check. RPC payloads carry endpoint origins only, never credentials, paths, or queries.
- **`dist/` must stay flat.** Local directory plugins ignore `package.json` `exports` and look for `server.js`, `index.js`, and `tui.js` directly in the directory, so local development points `plugins` at `<repo>/dist`.
- **TUI keys go through `context.renderer.keyInput`.** The host keymap attaches first, so `esc` and `ctrl+c` close the dialog before the browser's listener runs, and `preventDefault` in the browser only stops the focused input. The browser ignores keys with ctrl, meta, option, super, or hyper, consumes only keys it handles, and removes its listener when the dialog closes. Keys that close the dialog or open another one (`enter` on a row, `m`, `a`, and frame keys such as `/actualyze`'s `k`, `c`, and `b`) are consumed before the handoff, so they never reach the next focused input. In a keymap layer, inline commands (no `id`) are called without a `KeyEvent` and named commands receive it as the second argument of `run`; scout still reads keys through `keyInput`, because one listener routes every key by screen and focus (`src/tui-keys.ts`) and must leave printable keys to the search input while it has focus.
- **One dialog at a time.** `show`, `ui.dialog.prompt`, `ui.dialog.select`, and host commands run through `keymap.dispatch` (`model.list`, `provider.connect`) replace the open dialog and run its `onClose`. State that must outlive a dialog, such as an `/actualyze` session, lives outside it, and the dialog is shown again from that state.
- **Selecting a model goes through OpenCode's picker, pre-filled.** The TUI plugin API has no model setter, so `enter` on a model and `m` dispatch `model.list` and then type a search into the picker. The picker's search input sets `traits = { status: "FILTER" }` and focuses itself one tick after it mounts; scout polls `context.renderer.currentFocusedRenderable` every 16 ms for up to 1 s for a focused renderable with that trait, a string `value`, and an ID other than scout's own search, and assigns `value` once while it is empty. OpenTUI's `InputRenderable` emits `input` on a changed `value` (0.5.17 and 0.6.6, which OpenCode 2.1.3 ships), and the picker sets its filter from that event, as its own `setFilter` does. The match is duck-typed, never throws, and leaves an unfiltered picker when no field appears. A context has at most one pending pre-fill: a new handoff ends the earlier one, and so do plugin cleanup, the fill, and the timeout, each removing the timer and the key listener. Any keypress before the fill ends it too, because keys from the same input chunk run before the picker focuses its search and can replace the picker with another `FILTER` dialog (`ctrl+a` opens the provider list). That listener is attached during the handoff key's dispatch, which it never sees because OpenTUI calls the listeners it had when the dispatch began, and it is prepended because the host keymap prepends its own and stops the keys it handles. The search uses the host's names, not scout's: `<provider name> <model name>` while any integration has a connection, else the model name alone, because the picker fuzzy-matches every word (fuzzysort 3.1.0) against each model's `name` and a category that is the provider's name only while some integration is connected (`hasConnectedProvider`). The picker drops `status: "deprecated"` models before it searches, so `pickerBlocked` refuses them. The picker sorts zero-priced models and favorites first among the matches, so either can precede the model.
- **Dialog order is `show` then `set`.** `context.ui.dialog.show(render, onClose)` resets the size and placement, and `set` resets every option it omits, so call `context.ui.dialog.set({ size: "xlarge", centered: true })` after `show`. Renderables must be created inside the render callback; the reconciler's `createElement` throws outside it. `TuiRenderer.set` and `setStyledText` only mutate existing nodes and work anywhere. The TUI cleanup closes any open `/modelscout` or `/actualyze` dialog and refuses later opens from that context, because a plugin reload would otherwise leave it on screen.
- **The dialog render runs untracked.** Since 2.0.32 the host runs the render callback once per `show`, but inside a memo, so a reactive read during the render (`context.theme`, `context.themeMode`, `context.ui.model.current()`) would run it again and remount the dialog. `tui-session.ts` runs the render inside `untrack` from the host's `solid-js`, and a render that does run twice replaces the view it built before. Colors are never captured at build time: every paint calls `rolePalette(context)` again, and a `createEffect` owned by the dialog reads `context.theme` and `context.themeMode` and repaints on a change. Without `solid-js` the render runs tracked and a theme switch shows on the next timed repaint.
- **Styled text is assigned to the renderable.** The reconciler's `setProp("content")` stringifies anything but a string, so `TuiRenderer.setStyledText` builds an OpenTUI `StyledText` and assigns it to the text renderable's `content` directly; OpenTUI 0.5.17 repaints on that assignment. Every list row and detail line is one text node with styled chunks. The fallback view uses one plain string.
- **Dialog layout.** Return a content-sized root (no `flexGrow`/`minHeight`) bounded by `context.renderer.terminalHeight`. OpenTUI counts a box's padding inside its `width`, so the root's width is the whole dialog width, `min(116, cols - 2)`, with side padding 3 (the host's `DIALOG_INSET`) inside it, and content gets 6 columns less: 110 at 120 columns, 72 at 80. Its height is at most `min(30, rows - 5)`, including one bottom padding row: with the row the host's panel adds above the content, the dialog takes at most `rows - 4` rows. A frame card that replaces the list, and the key list over it, shrink the root to their lines plus the blank row kept above the footer. From 120 columns the list (58), a separator (3), and a preview of the selected row share the content width; the preview never takes focus or scrolls, and its `↓ N more` line ends in `· i`. The details screen (`i`, or `enter` on a provider header) takes the whole content width at every size, and a resize keeps it open. A renderer `resize` relayouts the existing nodes without showing the dialog again.
- **Theme from the dialog surface.** `rolePalette` in `src/tui-theme.ts` maps every view role to a `context.theme.surface("dialog")` token, matching the host's own dialogs. `text.faint` exists only from 2.0.32 and the pinned types lack it, so it is read as `unknown`, checked, and falls back to `text.muted`. The `brand` role is a hex color per `themeMode` (`#a855f7` dark, `#7c3aed` light), used only in `/actualyze`. The row list paints its own selection band (`selected` on `selectedBg`); the browser has no OpenTUI `select` widget.
- **`/actualyze` sessions and the key flow.** A session starts when `/actualyze` opens (slash, palette, or `a` in `/modelscout`) and ends when its dialog closes for any reason except the key prompt round trip. The session holds the pending-key marker, the links screen, and the integration and provider facts; only the latest session of a context is active. A save completion for an ended session changes nothing except one warning toast when the save was not confirmed; a completion that finds the location changed also ends the session and closes its own dialog (never a dialog that replaced it), with the same toast for an unconfirmed save. `k` runs only when the provider's `integrationID ?? "actualyze"` is `actualyze` and that integration offers a `key` method without form fields. An `undefined` prompt result (cancel, or another dialog replaced the prompt) ends the flow and the session without showing anything again; an empty string shows `/actualyze` again unchanged; a non-empty answer that arrives after the session ended (plugin cleanup) or at another location is dropped with a warning toast that the key was not saved; any other answer is trimmed, passed once to `client.integration.connect.key` with a 15 s timeout, and the reference is dropped. A rejection or timeout is "unconfirmed", never "not saved", because the host may have stored the key first. The key is never stored, rendered, logged, sent over RPC, or kept in session state. From the provider the TUI reads only `integrationID` and `settings.baseURL` (other settings can hold a plaintext `apiKey`), and reduces the base URL at once to an origin and a `customEndpoint` flag.
- **`/actualyze` state is derived, and claims only the catalog.** `deriveActualyzeState` is pure and maps every input combination to exactly one row, with `resolving` as the default; rows that show a discovery result need a current record (`resultEpoch === credentialEpoch`). After a submit, "checking" lasts until a current record's `credentialEpoch` is above the epoch at submit, or until any current record arrives once the payload's `instanceID` differs from the one at submit. An inference key cannot read identity, usage, spend, or budget, so the UI says "Catalog accessible" and never claims inference works.
- **RPC errors are plain objects.** Failures reject with `{ type, message }`, not `Error` instances (`rpc.unavailable`, `rpc.internal`, `rpc.invalid_input`). Pass the dialog's captured location in every RPC call's options; without it the server falls back to its own directory. RPC and bus event subscriptions filter by type only, so the TUI filters events by location itself.
- **No startup output.** Nothing writes to stdout or stderr. `console.warn` is for error conditions only.

## Commands

```
npm run check       # typecheck + lint + format:check + unit + E2E + compile + check:dist (CI gate, pre-push hook)
npm run test:run    # unit tests only
npm run test:e2e    # embedded-host E2E lane only
npm run fix         # eslint --fix + prettier --write
npm run compile     # tsup → dist/ with type declarations
npm run compile:dev # tsup → dist/ without declarations
npm run check:dist  # fail on runtime @opencode/* or effect imports in dist/
npm run build       # same as check
```

Pre-commit runs lint-staged (eslint --fix + prettier on staged files).

## Releasing

1. Bump the version in `package.json`.
2. Run `npm run check`, the live harness with `scripts/live-check.mjs`, and every scenario of `scripts/live-tui.mjs` (see CONTRIBUTING.md).
3. Commit, tag (`git tag vX.Y.Z`), push with tags.
4. CI: check → compile → npm publish (OIDC, provenance) → GitHub Release.

Do NOT publish manually.

## Commit Style

Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `chore:`, `refactor:`. Imperative summary, no trailing period.
